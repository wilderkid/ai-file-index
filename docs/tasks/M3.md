# M3 — USN 增量更新 + 快照

## 目标
索引在文件变化后 < 1 s 内更新；服务重启时从快照 < 1 s 恢复并追上停机期间的变化；日志被重置时安全地重新全量。

## 背景
- `FSCTL_READ_USN_JOURNAL`（0x900BB）输入 `READ_USN_JOURNAL_DATA_V1 { StartUsn, ReasonMask, ReturnOnlyOnClose: 1, Timeout, BytesToWaitFor: 1, UsnJournalID }`。
  `BytesToWaitFor > 0` 时阻塞直到有新记录，适合专用线程。
- 一次操作会产生多条记录（如 `RENAME_OLD_NAME` + `RENAME_NEW_NAME`）。用 `ReturnOnlyOnClose` 后通常只需看 `CLOSE` 记录的合并原因位；
  骨架中 `aifi_ntfs::reason::classify` 已实现映射（删除 > 改名 > 创建 > 修改），`VolumeIndex::apply` 已处理 4 种 `ChangeKind`。
- 错误：`ERROR_JOURNAL_ENTRY_DELETED`（游标落后于日志截断点）或 `journal_id` 变化 → `Error::JournalReset`，`aifi_core::catch_up` 已有约定。
  `FakeVolume::truncate_journal` / `reset_journal` 可模拟这两种情况。
- 快照：`SnapshotStore` trait（`FORMAT_VERSION`）。建议 `rkyv 0.8.18` 零拷贝 + `memmap2 0.9.12`，文件头含魔数、格式版本、卷序列号、`JournalCursor`、校验和。

## 要改的文件
- `crates/aifi-ntfs/src/win.rs`：`read_changes`
- `crates/aifi-ntfs/src/lib.rs`：把 `RawUsnRecord` → `ChangeEvent` 的转换写成纯函数（可测）
- `crates/aifi-core/src/snapshot.rs`（新）：`FileSnapshotStore: SnapshotStore`

## 验收标准 / 测试
- [ ] 假卷：创建 / 删除 / 重命名 / 跨目录移动 / 目录整体删除后，索引与"从头枚举"结果完全一致（随机 5000 步性质测试）。
- [ ] `truncate_journal` → `JournalReset` → `open_or_rebuild` 自动全量，结果正确。
- [ ] 快照往返：`save` → `load` 后所有路径一致；版本不符、序列号不符、文件损坏（随机翻转字节）都返回"需重建"而非 panic。
- [ ] 快照写入是原子的（写一半被杀不会留下可加载的坏文件）。
- [ ] Windows VHD 集成测试：创建文件后 1 s 内 `read_changes` 能反映。
- [ ] 200 万条目快照加载 < 1 s（release，贴数据）。

## 不在范围内
服务线程模型与调度（M6）、`recent_changes` 环形缓冲（M6）、非 NTFS 监控。

## 审查清单
- [ ] 没有调用 `FSCTL_CREATE_USN_JOURNAL` / `FSCTL_DELETE_USN_JOURNAL`
- [ ] 快照目录权限由调用方提供，本 crate 不硬编码路径
- [ ] rkyv 反序列化前做校验（`check_bytes`/validation），不信任磁盘数据
- [ ] 所有失败路径退化为全量重建，而不是崩溃
- [ ] PR ≤ ~400 行
