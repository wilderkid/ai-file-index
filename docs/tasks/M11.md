# M11 — v2：内容搜索（先定权限模型）

## 目标
`find_files` 支持"文件名缩小候选集 → 读内容二次过滤"的两阶段内容搜索，先支持纯文本，再支持 docx / xlsx / pdf 文本提取。

## 必须先决定：谁来读文件
服务以 SYSTEM 运行。如果由服务替调用方读文件内容，任何能连上管道的普通用户都能读到自己 ACL 不允许读的文件，
这是本地提权式的信息泄露。可选方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. MCP 端读 | 服务只返回候选路径，`aifi-mcp`（用户身份）读内容并过滤 | ACL 天然正确；服务保持"只看元数据" | 需修改 AGENTS.md 中"aifi-mcp 禁止直接读盘"的边界 |
| B. 服务模拟调用方 | 服务对每次请求 `ImpersonateNamedPipeClient` 后读文件 | 不改 crate 边界 | 模拟代码易出错；读文件期间线程以用户身份运行 |

推荐 A：改动集中、权限语义简单。这个决定要由人类确认后更新 AGENTS.md 第 2 节与 `docs/privacy.md`。

## 同一问题在文件名层面
文件名列表本身也没有按调用方 ACL 过滤（M6 只过滤了其他用户的 profile 目录）。在多用户机器上，
普通用户能看到自己无权访问目录里的文件名。至少要在 `docs/privacy.md` 写明这一点；是否进一步过滤另行讨论。

## 要改的文件（按方案 A）
- `crates/aifi-protocol`：`FindFilesParams.content: Option<ContentQuery>`（`#[serde(default)]`），`Capability::Content`。
- `crates/aifi-mcp/src/content.rs`（新）：对候选集读文件（≤ 1 MiB/文件、总读取上限、超时、跳过二进制、再次过黑名单）。
- `crates/aifi-query`：`PostProcessor` 接口落地（仅作为契约；实现放 MCP 端）。
- 文档提取（第二步）：docx/xlsx 是 zip+XML，可用 `zip` + `quick-xml`；pdf 文本提取依赖较重，单独评估。

## 验收标准 / 测试
- [ ] 无权限读的文件静默跳过，不报告其内容或存在性以外的信息。
- [ ] 读取上限都生效：单文件大小、候选数、总字节、总耗时。
- [ ] 黑名单在读内容前再检查一次（测试）。
- [ ] 内容不出现在服务端或 MCP 端日志里。

## 不在范围内
全文倒排索引（先做按需扫描，等实际需要再考虑）、OCR。

- [ ] 只读打开文件，不改访问时间以外的任何属性
